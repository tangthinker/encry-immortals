# 07 · 凭证导出与灾难恢复（对应母方案第七章）

> 母方案的恢复流程只有 4 步，但真实灾备中最常见的失败不是数据坏了，而是"Armor 字符串抄错一个字符"/"忘了某个参数"/"还原到一半发现磁盘不够"。本文补齐三件事：凭证的**可用性**、恢复的**可验证性**、以及**演练**。

## 7.1 恢复所需的最小信息集（**必须**明确告知用户）

| 项 | 是否必须 | 丢失后果 |
|---|---|---|
| `TargetDir` 全量（`data/` + `meta/`） | 是 | 无法恢复 |
| Armor Key（含 salt 与 KDF 参数） | 是 | **永久无法恢复**。整个方案的单点 |
| 主密码 | 是 | 同上 |
| `state.db` | 否 | 可重建，只会丢失"未回滚"的可验证性（见 7.5） |
| 工具二进制（含版本） | 否 | 可由格式版本重建；但 **v1 二进制必须能读 v1 数据**，见 12 章 |

**必须**：`apex init` 结束时打印"三件套"提示，并写入 `~/.config/apex-vault/RECOVERY.txt`（控制平面，可打印）。**禁止**在 `TargetDir` 内放任何人类可读提示（违反盲盒原则）。

## 7.2 `vault.meta` 的冗余策略

母方案要求"`vault.meta` 不存放在目标目录"，这条**必须**保留（否则等于把锁和钥匙放一个盒子里，云端一拖库就能离线撞库）。

但代价是"丢了 `vault.meta` = 全灭"。因此**建议**三条冗余，且都要用户显式建立：

| 位置 | 形式 | 建议 |
|---|---|---|
| 密码管理器 | Armor Key V2 字符串（02 章 D-16） | **必须**至少一份 |
| 打印 / 手抄 | 同上，按 5 字符分组便于核对 | **建议**一份离线纸质 |
| 第二台可信设备 | `~/.config/apex-vault/vault.meta` 原文件 | 可选；注意该设备的 `state.db` 与本机不同步 |

**禁止**：把 Armor Key 或 `vault.meta` 放到 `TargetDir` 或其任何子目录、或同一网盘目录。`apex doctor` **必须**主动检查：扫描 `TargetDir` 及其父目录一层内是否存在名为 `vault.meta` 的文件，命中即告警。

## 7.3 Armor Key 的手抄可用性（决策 D-16 的落地）

母方案用 Zstd + Base64。实际打印出来含 `+ / =`，手抄错误率极高且无自检。修订要求：

| 项 | 要求 |
|---|---|
| 字母表 | Crockford Base32（去除 I L O U），大小写不敏感 |
| 分组 | 每 5 字符一组，用 `-` 分隔 |
| 行宽 | 72 列换行，便于 A4 打印与密码管理器多行字段 |
| 校验 | 末尾 4 字节 CRC32C；import 先验 CRC 再解压 |
| 前缀 | `APEX-KEY-V2-`（便于搜索，且标识版本） |
| 长度估计 | 400 B JSON → zstd ≈ 300 B → base32 ≈ 480 字符 ≈ 96 组 ≈ 7 行。**可打印，不可口述** |

**必须**：`apex export-key` 同时输出 (a) 单行版（给密码管理器）、(b) 分组多行版（给人眼核对）。**必须**提示"该字符串等同于主密码之外的盐与参数，请与密码分开存放"。

## 7.4 灾难恢复的标准流程（**必须**逐条实现）

~~~text
全新机器：
 1. 安装同版本或更高版本的 apex（必须能读旧格式，见 12 章兼容矩阵）
 2. apex init --join <TargetDir>        // 不生成新 vault，进入"待导入"状态
 3. apex import-key                     // 交互式粘贴 Armor Key，先验 CRC32C
 4. apex doctor                         // 检查 vault_id 与 TargetDir 内 journal 是否匹配
                                        // 检查磁盘剩余空间 >= 需求估算
                                        // 检查 TargetDir 条目完整性
 5. apex verify --size                  // 可选但强烈建议：确认所有 pack 都在
 6. apex restore <DestDir> --at-latest --anchor <短码>
                                        // 无短码时要求 --i-accept-unverified
 7. apex verify --deep --source <DestDir>   // 可选：抽样对比还原结果
~~~

**必须**：
- 第 4 步的"磁盘空间预检"要在**解密任何数据之前**完成，所需空间 = 最新 checkpoint 的 `tree` 中 `size` 求和（不需要解密任何 pack）。
- 第 6 步的 `DestDir` **必须**为空或不存在（除非显式 `--overwrite`）。灾备时最忌讳把数据混进一个已有目录。
- 还原中断后重跑同一命令，靠 `.apex-restore-progress` 续解（见 05 章）。

## 7.5 无锚点恢复（**必须**显式告警的路径）

新机器上没有 `state.db`，因此**无法**证明云端数据未被回滚或截断。此时程序有三种选择，**必须**选第三种：

| 选择 | 评价 |
|---|---|
| 静默继续 | **禁止**。用户会以为恢复成功，实际可能拿到一个月前的数据 |
| 直接拒绝 | 过于粗暴：真丢机器时用户没有锚点，等于永远无法恢复 |
| 告警 + 显式越权标志 | **必须**采用 |

告警文案（**必须**包含）：

~~~text
警告：本机没有该 vault 的可信锚点，因此无法排除云端数据被回滚或截断的可能。
     你将获得的是「当前可见的最后一页」对应的状态，而非「本应存在的最后一页」。
     若记录过水位码，请用 --anchor <短码> 校验；否则加 --i-accept-unverified 继续。
~~~

**必须**：恢复完成后在输出与 `state.db` 中都标记本次恢复为 `UNVERIFIED`，该标记随所有后续 status 输出持续可见，直到用户显式执行 `apex status --clear-unverified`。

## 7.6 部分数据丢失时的抢救

场景：云端丢了若干 pack 但 journal 链完整；或 `meta/` 丢了最后几个 journal。

| 场景 | 能救回什么 | 程序行为 |
|---|---|---|
| 少数 pack 丢失 | 其余文件 100% 恢复；受影响文件全部失败 | 列出受影响文件清单（沿 `slices[].pack_idx` 反查），继续还原其余，退出码 13 |
| 尾部 journal 丢失 | 恢复到最后一个可解密 seq | 报 `E11 CHAIN_TRUNCATED`，提示"若记得水位码，可确认少了几次提交" |
| 中间 journal 丢失 | 链断裂，之后全部不可信 | 报 `E11 CHAIN_BROKEN at seq=N`，**拒绝**继续（除非 `--stop-at N-1`） |
| journal 全丢但 pack 都在 | 数据在但不可解（pack 是哑存储） | 报 `E12 无索引`。`apex salvage` 仅导出 pack footer（03 章）中的切片清单供人工排查，**不做**自动拼装——拼错比不拼危险 |

## 7.7 恢复演练（**必须**写进文档，否则灾备等于没做）

| 频率 | 动作 | 判定 |
|---|---|---|
| 每次 backup | 自动校验新 journal 的 `prev_hash` 与本地锚点 | 失败即告警 |
| 每月 | `apex verify --sample 8` | 抽样 pack 的 sha256 全通过 |
| 每季度 | 在空临时目录做 `restore --at-latest --sample 100`，比对抽样文件内容 | 内容逐字节、mode 与 mtime 一致 |
| 每半年 | 完整 restore 到外部磁盘一次 | 全量成功 |
| 每年 | 从 Armor Key 重新 `import-key` 一次 | CRC 与解密都通过（证明抄件仍可用） |

**必须**：`apex doctor` 读取演练记录（存本地 `state.db`），超过 90 天未演练时在 status 中提示。

## 7.8 口令不可更改：对灾备流程的影响

- 本系统**不支持**修改主密码（见 02 章 D-01R 与 2.8）。因此"在新机器上恢复后顺便换个密码"是一个**不存在**的操作，不要为它设计任何流程。
- 唯一能更换口令的手段是 `apex compact --new-identity`：重建一个全新库（新 salt、新 vault_id、新 key），再重新 export-key 并把本地配置指向新库。**必须**在文档中把它标为"小时级的重操作"，不是日常操作。
- 反过来，这条约束抬高了 init 阶段的门槛：密码强度检查**必须**是硬要求（02 章 2.8），init 完成后**必须**提示"主密码无法更改"，并在 RECOVERY.txt 里再写一遍。
- `state.db` 仍记录 `last_export_unix`，用途变为"检测导出的 Armor 是否落后于当前 vault.meta"：正常流程下二者应当同步，若不匹配说明用户手工替换过控制平面，值得告警。

## 7.9 待确认

1. 是否提供"把 `vault.meta` 拆成 N-of-M 分片（Shamir）"？**结论**：v1 不做，但格式上不排斥（Armor 本身就是字节串，外层套 Shamir 不影响格式）。若做，**必须**是独立子命令，不改线格式。
2. 是否支持"忘记主密码但记得 Armor Key"？**不可能**——Armor 里没有密钥，只有盐与参数。**必须**在 UI 上写清，避免用户产生错误期待。
