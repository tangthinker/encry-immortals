# 08 · 威胁模型（新增章节）

> 母方案用了大量"防篡改""无法展开离线撞库""网盘服务器仅能观察到高熵二进制"这类表述，但没有定义攻击者的能力边界。没有威胁模型的方案，其安全主张无法被验证，也无法判断某次实现取舍是否可接受。本文给出 A0–A5 分级、逐条"防 / 不防"矩阵、以及成本估算。

## 8.1 资产

| # | 资产 | 泄露影响 | 丢失影响 |
|---|---|---|---|
| A1 | 源文件明文 | 灾难级（内容即目的） | 灾难级（备份失去意义） |
| A2 | 源文件路径与目录结构 | 高（文件名常比内容更敏感） | 中 |
| A3 | 历史版本（含已删除文件） | 高（可能包含已销毁的敏感版本） | 低 |
| A4 | 备份规模与变更节奏 | 中（侧信道） | 无 |
| A5 | 主密码 | 灾难级 | 灾难级 |
| A6 | Armor Key（salt + KDF 参数） | 中（单独无用，与密码联合才有用） | 灾难级 |

## 8.2 攻击者分级

| 级别 | 能力 | 现实对应 |
|---|---|---|
| A0 | 被动网络监听 | 公共 Wi-Fi、ISP |
| A1 | 云端只读：拿到 Target 全部字节，不能写 | 网盘被拖库、供应商内部访问、账号被查看 |
| A2 | 云端可写：能改/删/替换 Target 内文件 | 账号被盗后有写权限、恶意同步客户端 |
| A3 | A2 + 能回滚整个目录到旧状态 | 网盘版本历史功能被滥用、快照恢复被利用 |
| A4 | 本地只读：能读 `~/.config/apex-vault/` 与 `state.db`，但不能改 | 本地恶意软件、备份到不可信云盘的 home 目录 |
| A5 | 本地可写：能改任意本地文件、注入进程 | 本机被完全控制 |

## 8.3 防 / 不防矩阵（**必须**与实现一致）

| 威胁 | A1 | A2 | A3 | A4 | A5 |
|---|---|---|---|---|---|
| 读取文件内容明文 | ✅ 防（AEAD） | ✅ | ✅ | ✅（控制平面无明文数据） | ❌ 不防 |
| 读取文件路径 | ✅ 防（path 在 journal 密文内） | ✅ | ✅ | ⚠️ 部分：`state.db` 只存 `HMAC(path)`（D-13），但 journal 名的时间戳泄露变更节奏 | ❌ |
| 拼凑出文件结构 / 识别文件类型 | ✅ 防（slice 无魔数、无固定长度、压缩后再加密） | ✅ | ✅ | — | ❌ |
| 修改 pack 内容 | ✅ 检测（tag + journal 中的 `packs[].sha256`） | ✅ | ✅ | — | ❌ |
| 切片重排 / 跨包搬运 | ✅ 检测（AAD 绑定 pack_id/offset/index/txn_id，D-02） | ✅ | ✅ | — | ❌ |
| 插入伪造的 journal | ✅ 防（AEAD + 链） | ✅ | ✅ | — | ❌ |
| 删除中间的 journal | ✅ 检测（链断裂，`E11`） | ✅ | ✅ | — | ❌ |
| **删除末尾的 journal** | ⚠️ 仅本地有锚点时可检测（D-04） | 同 | ❌ 若攻击者同时清本地锚点 | — | ❌ |
| 整目录回滚到旧版本 | ⚠️ 仅本地有锚点时可检测 | 同 | 同 | — | ❌ |
| 离线撞库（拿 Target + 猜密码） | ⚠️ 依赖 Argon2 参数（见 8.4） | 同 | 同 | — | — |
| 判断"某个已知文件是否被备份过" | ✅ 防（随机 nonce，密文不可比） | ✅ | ✅ | — | ❌ |
| 从密文规模推断数据量 | ❌ 不防（体积泄露是固有的） | ❌ | ❌ | — | ❌ |
| 读到主密码 | ✅（不落盘、不进 argv） | ✅ | ✅ | ❌ 若用户把密码写进配置文件 | ❌ |
| 勒索：改坏云端数据后勒索用户 | ✅（本地有源文件时不构成勒索） | — | — | — | — |
| 勒索：删光云端 + 删光本地 | ❌ 不防 | ❌ | ❌ | — | — |

图例：✅ 方案内已防；⚠️ 有条件防（条件写在该行或对应章节）；❌ 明确不防。

## 8.4 离线撞库成本估算

假设：攻击者拿到 Target 全量（含 `vault.meta`，其中 `auth_verifier` 是唯一的密码校验点），离线尝试密码。注意：无论是否引入 DEK 封装层，攻击者都只需"一次 Argon2 派生 + 一次 AEAD 验证"即可判定一个候选密码，因此撤销 DEK 层不降低破解成本的下限。

单次尝试成本 = Argon2id(候选密码, salt, t=3, m=256 MiB, p=1) 的计算成本。
以 `m=256 MiB, t=3` 计，单次派生的"内存 × 时间"乘积是 GPU 的天然瓶颈：**每次尝试需要 256 MiB 独立内存空间**，一块 48 GB 显存的消费级 GPU 理论上并发约 180 路，其吞吐量相对无内存硬约束的 SHA-256 类 KDF 下降 3–4 个数量级。

**数量级判断**（不同硬件差异巨大，此处只给保守区间，不作为精确承诺）：

| 密码强度 | 候选空间量级 | 在 A1 攻击者（租用 GPU 集群）下的实际风险 |
|---|---|---|
| 6 位纯数字 | 10^6 | 分钟到小时级 → **不安全** |
| 8 位随机字母数字 | 10^14 | 数十年以上 → 尚可 |
| 4 个随机单词（Diceware，约 51 bit） | 2×10^15 | 数十年级 → **推荐** |
| 6 个随机单词 | 10^23 | 无实际风险 → 推荐用于长期归档 |

**必须**：`init` 时做基础强度检查（长度、字符集、是否在常见字典前 10 万条内），弱密码**必须**给出明确警告但不阻止（用户有权选择，但要知情）。**建议**直接推荐"4 个随机单词"或生成 24+ 字符随机串。

**必须**：KDF 参数不可下调（02 章 2.6 的下限 128 MiB 是硬约束），且参数与密文一起保存，攻击者永远享受不到"参数被调低"的好处。

## 8.5 侧信道

| 通道 | 泄露内容 | 缓解 |
|---|---|---|
| 文件大小 | 每次提交的数据量 | 不缓解（固有的）。可选 `--pad-to` 补齐（**不做**：补齐反而形成更强的长度特征模板） |
| 文件数量 | 变更文件数 | 不缓解 |
| 修改时间 | 活跃时间段 | 不缓解（mtime 与文件名时间戳一致是必要的一致性） |
| journal 序号 | 提交次数 | 不缓解 |
| journal 数量的时间序列 | 用户活跃规律 | 可选 `--jitter` 在时间上抖动（**不做**，收益低、复杂度高） |
| 内存访问 | Argon2 的访问模式 | Argon2id 已设计为抗侧信道 |
| 解密耗时 | 文件大小 | 固有的 |
| 错误信息 | 密码正确与否 | 统一文案（02 章 2.7） |
| 退出码 | 同上 | **必须**统一：密码错误一律 10，不区分"用户不存在"之类的细分 |

## 8.6 明确不做的事（避免过度设计）

| 不做 | 理由 |
|---|---|
| 抗流量分析（恒定上传速率） | 成本远超收益，且用户可以用网盘限速间接实现 |
| 抗"服务商主动删档" | 端到端加密工具无法阻止对方不存储。缓解只能靠多副本（用户自选） |
| 抗本地已被完全控制（A5） | 任何本地加密工具在不安全主机上都无效。**必须**在文档里直说 |
| 内存中明文的完美擦除 | Go 运行时无法保证。做到"尽力 + 极短驻留时间" |
| 隐写 / 把密文藏进图片 | 母方案选择的是"伪装成普通二进制"，不是隐写。后者带来的体积放大与脆弱性不值得 |
| 与"不信任的第三方"共享 vault | 单一密钥体系不支持。若需要，另立 vault |
| 前向保密（密钥泄露不影响历史） | 这会与"不可变追加"冲突（每版数据用不同密钥需要额外的密钥链）。**结论**：v1 不做，但在 02 章的 HKDF info 命名空间里预留 `-v3` 位置 |

## 8.7 假设与依赖

**必须**如实声明本方案的信任前提：

1. 用户的操作系统与 Go 标准库的 `crypto/*` 实现未被攻破；
2. `golang.org/x/crypto` 的 Argon2id 与 chacha20poly1305 实现正确（这是唯一无条件信任的第三方代码）；
3. 主密码没有通过旁路泄露（截图、键盘记录、写进脚本、留在 shell 历史）；
4. 用户确实做了 Armor Key 的异地冗余（07 章）；
5. 用户没有把 `~/.config/apex-vault/` 放进任何同步目录。

第 5 条**必须**由 `apex doctor` 自动检查：若控制平面目录位于已知同步目录（Dropbox / OneDrive / iCloud / 用户配置的 TargetDir）之下，立即告警。

## 8.8 密码学组合的合规性说明

本方案没有发明基元，只做了一个**组合**：Argon2id（口令→MasterKey）→ HKDF-SHA256（MasterKey→4 把子密钥，salt=vault_id）→ XChaCha20-Poly1305（数据）。每一步都是标准构造：

- 口令 → KDF → 用 HKDF 做域名分离的多子密钥，是 KDF 链的标准用法（Tink keyset、age passphrase 模式同构）；
- 每段独立 nonce 的 AEAD 是标准的分段加密模式（Tink streaming AEAD、age 的 chunked 格式同构）；
- 每段 AAD 绑定位置信息是防止分片重排的标准做法。

**结论**：无需通过密码学审计即可建立基本信心，但**建议**在 1.0 前做一次第三方代码审计，重点是 03 章的解析器防御与 04 章的重放规则。

## 8.9 待确认

1. 是否提供"多密码可解锁同一库"（团队成员各自密码）？**结论**：不做。在"单 MasterKey、口令不可变更"的前提下，多密码必须重新引入密钥封装层（即已撤回的 D-01），与当前取舍冲突。
2. 是否需要"可否认性（duress password）"？**结论**：不。可否认性在此场景下会大幅增加格式复杂度，且密文本身已经不可区分内容。
