# 11 · 容量、压缩与整理（新增章节）

> 母方案明确"剔除数据释放（Eviction）"，这是正确的简化，但它带来两个必须正面回答的问题：**容量怎么算**、**没有回收怎么办**。回避这两点，方案在运行三个月后就会遇到"云盘满了"的现实。

## 11.1 容量公式

单次提交 `k` 的新增字节（近似）：

~~~text
Δpack(k)  = Σ_f  ceil(size_f / S) × (envelope 开销)  +  Σ_f  compressed(size_f)
            其中 envelope 开销 = 34 + 16 = 50 B
Δjournal(k) ≈ 120 B × op_count  +  32 B × slice_count  +  1 KiB 固定开销
sum        = Δpack(k) + Δjournal(k)
~~~

累计（N 次提交、每次都改动 D 字节）：

~~~text
Total(N) ≈ N × (D × r + 50 × ceil(D / S) + 120 × op_count + 1 KiB)
           r = 压缩后的残留比例（随机数据≈1.0，文本≈0.2–0.4）
           S = slice_plain_bytes
~~~

**实例**：

| 场景 | 每日变动 | 压缩率 r | 一年累计 |
|---|---|---|---|
| 文档 + 少量代码 | 20 MB | 0.3 | ≈ 2.2 GB |
| 照片库（JPEG 已压） | 500 MB | 0.99 | ≈ 180 GB |
| 混合个人数据 | 200 MB | 0.7 | ≈ 51 GB |
| 每次全量拷贝（无增量） | 100 GB | 0.6 | 不可行 |

**必须**：`apex status` 输出当前 total 与近 30 天日均增量，并给出"按当前速率，云盘 X GB 还能用 Y 天"的线性外推（明确标注"线性外推，仅供参考"）。

## 11.2 决策 D-11 的容量收益

| 数据类型 | 不压缩 | zstd level 5 | 收益 |
|---|---|---|---|
| 源代码 / 文本 | 1.00 | 0.25–0.35 | 3–4× |
| JSON / 日志 | 1.00 | 0.08–0.15 | 7–12× |
| 未压缩位图 | 1.00 | 0.9 | ≈1×（不值得，但无害） |
| JPEG / MP4 / ZIP | 1.00 | 0.99–1.00 | 无（由"不可压缩检测"跳过，省 CPU） |
| 密文 / 已加密归档 | 1.00 | 1.00 | 无 |

**必须**：不可压缩检测（03 章 3.4）保证不会为了 1% 收益浪费 3 倍 CPU。

## 11.3 去重：明确不做，以及代价

| 方案 | 收益 | 为什么不做 |
|---|---|---|
| 全局内容寻址去重（FastCDC + 全局索引） | 同内容多路径、多版本复用，可能省 30–60% | ① 需要跨文件哈希索引，索引本身要存在某处（存本地＝灾难恢复失效，存云端＝破坏盲盒）；② 与"不泄露内容存在性"冲突（同一块出现两次在日志里可见）；③ 与"纯追加不可变"逻辑上不冲突，但让 GC 变成必需品 |
| 同文件内版本间去重 | 大文件改动一点点就传整份 | 同上 |
| 文件级去重（同 size+hash 只存一份） | 小 | 引入"路径 → 共享 pack"的多对一引用，DELETE 语义立即复杂化 |

**结论**：v1 不做任何去重。**必须**在文档与 `backup --help` 里直说：**同一文件改一版就多占一份空间**，这是不可变追加的必然代价。

**代价量化**：一个 1 GB 的数据库文件每天改一次，一周就是 7 GB。若这是用户的真实负载，应引导到 `compact`（11.4）或建议改用其他方案。

## 11.4 决策 D-12：`compact` 是唯一的回收出口

不引入 eviction（服务端删除语义），而是"重建一个新库、整体切换"。

~~~text
apex compact --out <NewVaultDir> [--at <seq>] [--new-identity]

1. 读旧库全部 journal（或 checkpoint + 增量）→ 得到目标快照的虚拟树
2. 在 NewVaultDir 中重建：新 salt、新 MasterKey 派生链（若 --new-identity）、新 vault_id
3. 只写"当前仍被引用的切片"，重新打包（此时自然获得新的 pack 边界）
4. 生成 seq=1 的 journal（kind=0，全量 ops 等价于第一次备份）
5. 用户可以：
   a. 把新库上传到一个新网盘目录，确认可用后再删除旧目录
   b. 或把旧目录改名（用户自己操作），把新目录挪过来
~~~

**必须**：
- `compact` **绝不删除**旧库的任何文件。删除由用户手工完成，且旧库保留期**建议** ≥ 30 天。
- `compact` 后新库的 `vault.meta` 是新的（salt 变了），**必须**重新 `export-key`。
- `compact` 是唯一会改变 `vault_id` 的操作，因此旧 Armor Key 对新库无效——这个提示**必须**醒目。
- 空间估算：`compact` 的峰值磁盘占用 = 新库大小（旧库不动），**必须**在开始前检查剩余空间。

### 与"删除的历史"的关系

用户删掉一个 10 GB 文件后，那 10 GB 依然在 `data/` 里。要真正回收：

~~~text
apex compact --out /new/path      # 新库不含已删除文件的切片
~~~

这是**唯一**路径。**必须**在 `log` 与 `status` 中提示"存在 X 个已删除但仍占用 Y GB 的历史版本，可用 apex compact 回收"。

## 11.5 增长控制建议（写给用户，不是写进协议）

| 手段 | 效果 |
|---|---|
| `scan.exclude` 排除缓存/构建产物 | 通常减少 50%+ 的无效增量 |
| 提高 `slice_plain_bytes`（32 → 64 MiB） | 减少切片数与 packing 开销，但增大最小读取粒度 |
| 定期 `compact` | 回收已删除历史；重置 pack 边界 |
| 降低 `checkpoint.every_commits` | 加速 restore，但增加单次提交体积 |
| `session_max_mib` | 单次备份上限，避免一次写入 500 GB 打爆网盘同步 |

## 11.7 待确认

1. 是否需要"自动 compact 到临时目录并在阈值触发"？**结论**：不做。自动重建库的风险远大于收益（一次 bug 就毁掉备份）。
2. 是否允许 `compact` 读一个不完整的旧库（缺 pack）？**结论**：允许，但**必须**在输出中列出哪些文件因 pack 缺失而被丢弃，并要求 `--accept-data-loss` 显式确认。
