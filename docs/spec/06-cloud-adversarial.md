# 06 · 网盘对抗与远端鲁棒性（对应母方案第六章）

> 母方案第六章的"原子换入"与"伪装命名"是对的两条，但把网盘客户端当成"只会顺序抓取的哑终端"。现实中它有明确的工程限制（目录条目数、单文件大小、乱序到达、忽略规则不可控）。本文把这些变成假设表和对策。

## 6.1 网盘客户端行为假设表

**必须**以实现与测试中的下表为准，而不是以"理想同步客户端"为准。

| 属性 | 假设 | 对本方案的影响 |
|---|---|---|
| 抓取粒度 | 目录项级别，新建文件即触发 | 原子 rename 是唯一有效的保护 |
| 是否遵守忽略规则 | **不可靠** | 不能假设 `.tmp/` 不会被上传（见 6.2） |
| 到达顺序 | **不保证** | journal N+1 可能先于 N 到达（见 6.6） |
| 是否重命名 | 少数客户端会"整理"隐藏文件 | 文件名不可承载语义，AAD 不依赖文件名（见 03 章） |
| 单文件大小 | 2–4 GB（视会员） | pack 128 MiB 安全 |
| 目录条目数 | 数百到数千级开始明显变慢 | **必须**做目录分片（见 6.3） |
| 断点续传 | 大文件通常支持 | 但不保证；128 MiB 是"失败重传可接受"的量级 |
| 秒传 / 去重 | 有（服务端按内容 hash） | 见 6.5 |
| 冲突处理 | "保留两份"或"提示用户" | 本方案从不覆盖，冲突面被消除 |
| 是否压缩存储 | 部分服务端会 | 无影响（密文不可压） |

## 6.2 `.tmp/` 被同步的现实（决策 D-06 的代价）

母方案写"网盘需忽略"，但这是**用户无法在所有客户端上兑现**的假设。本方案的取舍是：**接受 `.tmp/` 会被同步，改为让它的产物无害**。

| 措施 | 说明 |
|---|---|
| 暂存文件伪装 | `.tmp/` 内文件同样命名为 pack_<ts>_<rand>.dat，同步上去也只是看不懂的二进制 |
| 短命 | 正常流程下 `.tmp/` 内文件存活时间 = 单次 pack 写入耗时（秒级到分钟级） |
| 启动清扫 | 每次 backup 启动时删除 `.tmp/` 中 mtime > 24h 的条目 |
| 不做云端清理 | 已上云的残片**不主动删除**——删除云端文件是断链或触发回收站的高风险操作，交给用户人工处理 |
| 可外置 | `storage.staging_dir` 指向 Target 外目录，但强制同卷校验（见 01 章） |

**必须**：apex status 报告 `.tmp/` 条目数与字节数，让用户知道云端可能出现多少残片。

## 6.3 目录条目膨胀（母方案完全未覆盖）

### 问题

- 每次 backup 产生 1 个 journal + 若干 pack。每日一次、持续三年 → `meta/` 有 1095 个文件。
- pack 数量取决于变动量：每日 1 GB 变动 / 128 MiB ≈ 8 个 pack → 三年 8760 个 pack。
- 百度网盘 / 夸克对单目录条目数敏感：上千文件后列表加载与增量扫描显著变慢，双向同步场景更易出现卡顿与"同步异常"。

### 对策（**必须**）

| 对象 | 分片规则 | 代价 |
|---|---|---|
| `data/` | 按 pack 创建时间分月：`data/2026-03/` | restore 需枚举子目录再排序；data 下多一层 |
| `meta/` | **不分片**，保持单层 | 三年 1095 个文件，可接受 |
| 分片阈值 | 单目录条目数 > 5000 时 status 告警 | 无 |

**关键取舍**：meta 不分片的理由是 restore 必须"按文件名全局排序"。一旦分片，排序变成"先按目录名再按文件号"，并要求目录名与序号严格对应，极易出错。**结论**：meta 保持单层，靠 checkpoint（04 章 D-14）把 restore 的解密量压到常数级；目录条目数到 10^4 量级之前对网盘不致命。

**必须**：`data/` 分片后，journal 的 `packs[].name` **必须**存**相对路径**（`data/2026-03/pack_...dat`），而不是裸文件名。否则 restore 需要全盘遍历才能定位一个 pack。

## 6.4 远端校验（`apex verify`）

母方案完全没有"怎么知道云端文件是好的"。有了 04 章的 `packs[]` 指纹，可以低成本实现：

| 模式 | 代价 | 能查出什么 |
|---|---|---|
| `verify --size`（默认） | 只 stat | pack 被截断/丢失（size 不符）、journal 缺失 |
| `verify --sample N` | 下载 N 个随机 pack 全量 SHA-256 | 抽样完整性 |
| `verify --deep` | 全量下载 + 解密 + 逐切片明文校验 | 端到端正确性（最慢，等价于"不落盘的 restore"） |

**必须**：
- 输出包含"云端 pack 总数 / journal 引用总数 / 本地 pack 总数"三个数字；
- 检测到缺失时**必须**明确指出"哪些文件受影响"（沿 `slices[].pack_idx` 反查 ops），而不是只报一个数字；
- `verify --deep` 在 `--jobs` 下并发，内存上限受 05 章约束。

## 6.5 秒传 / 服务端去重的双面性

| 面 | 说明 |
|---|---|
| 优点 | 无。随机 nonce 使每次加密结果不同，本方案**永远享受不到秒传** |
| 缺点 | 同一文件改一版就多占一份云盘空间（纯增量） |
| 安全面 | **这恰恰是特性**：若做确定性加密，服务端就能通过"是否秒传成功"判断"我是否备份过这个文件"，等于泄露内容存在性 |
| 结论 | 保持随机 nonce，**不做**确定性加密，**不做**服务端去重优化。容量线性增长必须在 11 章的容量公式里正面写清 |

## 6.6 乱序到达与最终一致

网盘客户端可能先传完 `meta/00000012.journal` 再传 `data/2026-03/pack_X.dat`，产生一个**瞬时**不一致窗口。

**必须**：
1. backup 的提交顺序保证"pack 先于 journal"（05 章 S3 → S6）。因此正常上传顺序下，云端不会出现"journal 到齐但 pack 未到"的**最终**状态，只可能有瞬时态。
2. restore 打开 pack 前先 stat 校验 size，不符则明确报错 `E13 pack 尚未同步完成或已损坏：<相对路径>`，提示"请等待网盘同步完成后重试"，退出码 13。
3. restore 提供 `--wait-for-packs <duration>`：在该时间内周期性重试缺失的 pack（默认关闭）。这是唯一允许"等待"的地方，其余时刻一律 fail-fast。
4. **禁止**在 pack 缺失时"跳过该文件继续还原"。那会产出一个看起来成功的残缺还原，是灾备场景最危险的行为。

## 6.7 伪装命名的审计清单

母方案的对策正确，此处补一份可直接对照实现的检查表：

| 检查 | 通过标准 |
|---|---|
| 扩展名 | 只有 `.dat` 与 `.journal`；无 `.enc` / `.crypto` / `.zip` / `.bak` |
| 文件名熵 | `pack_<13位数字>_<6位36进制>`，无源文件名片段、无用户语义 |
| 文件头 | 前 16 字节为随机 `pack_id`；32 B 头内**不含** `PK\x03\x04`、`\x89PNG`、`%PDF` 等魔数，也不存在可被指纹化的固定前缀 |
| 熵分布 | 除 32 B pack 头与每切片 34 B 信封头（ver_alg/env_len/plain_len/codec/nonce）外全为密文；这两处头不含任何用户语义，不泄露文件类型 |
| 长度分布 | 128 MiB 上限内变长；**禁止**补齐到固定大小（固定大小是更强的特征） |
| 时间 | 文件名时间戳与文件 mtime 一致（否则是可疑特征） |
| 目录 | `data/YYYY-MM/`、`meta/`；无 `backup/` `vault/` `crypto/` 等语义目录名 |

**建议**：`apex doctor --camouflage` 自动跑这张表（对样本做检查），把它变成 CI 的一项。

## 6.8 上传期间的用户体验

- backup 完成（journal 已 rename）即返回成功，**不等待**网盘上传完成——程序无法感知客户端状态，也不应假装能感知。
- 输出提示语固定为：`已提交 seq=N（本地完成）。云端同步由网盘客户端负责，可用 apex status 对比本地与云端条目数。`
- **禁止**在程序内轮询网盘客户端状态（无标准接口，且会引入对特定厂商的依赖）。

## 6.9 待确认

1. 是否需要 `--sync-wait` 之类"检测到同步完成再退出"的功能？**结论**：不做。无法可靠检测，做了会给虚假安全感。
2. 是否针对特定网盘（夸克/百度/OneDrive）做适配层？**结论**：不做。保持"任何文件系统同步工具都可工作"是更大的价值。
